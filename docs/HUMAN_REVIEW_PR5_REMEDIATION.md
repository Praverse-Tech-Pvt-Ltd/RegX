# PR #5 Human-Review Remediation

This document records the remediation of the blocking findings from the
focused human-review gate performed against REGX PR #5
(`regx/feat/fda-iid-foundation` → `regx-main`), which returned an overall
result of **FAIL**. It supplements, and does not replace or rewrite, the
original review record.

Original review result: **FAIL** — 1 Critical, 1 Major, 2 Minor findings.

## Traceability table

| Finding ID | Classification | Original defect | Root cause | Code correction | Tests added | CI evidence | Residual risk | Closure status |
|---|---|---|---|---|---|---|---|---|
| HR-01 | Critical | Mapping lifecycle transitions were not validated against the mapping's current status. A mapping could be approved directly from `PROPOSED`, `RETURNED`, or even `REJECTED`, bypassing mandatory review. | Each mapping-action view (`submit-review`, `approve`, `reject`, `return`) mutated `status` directly based on which URL was hit, with no check against the mapping's *current* status. | Added `backend/fda_data/mapping_transitions.py`: a single authoritative `validate_mapping_transition(mapping_type, current_status, action)` transition table covering all four mapping types (route, dosage_form, unit, substance). `_MappingActionViewBase` in `backend/fda_data/views.py` now: (1) opens a DB transaction, (2) re-fetches the row with `select_for_update()`, (3) calls the transition function before any mutation, (4) raises a structured 400 (`IllegalMappingTransition`) with no mutation and no audit event on failure, (5) only mutates/saves/emits audit on a legal transition. | `backend/fda_data/tests/test_mapping_lifecycle_transitions.py` — 15 named regression tests (VP cannot approve PROPOSED/RETURNED/REJECTED; APPROVED/REJECTED terminal; legal forward transitions per type; Doer cannot approve; submitter cannot self-approve; illegal transition → structured 400 with no audit event; concurrent-approval race resolved via `select_for_update`, run against both substance and route mapping types). | Backend CI (pytest) on the final SHA — see Section "CI evidence" below. | Low. The transition table is centralized and unit-tested per (mapping_type, action, status) combination; any future mapping type must be added to the table explicitly or `validate_mapping_transition` fails closed with "Unknown mapping type". | **CLOSED** |
| HR-02 | Major | No shipped API or import path could ever create a `PROPOSED` `SubstanceSynonymMapping`. The only way to start the mapping-review workflow was direct Django shell / ORM insertion — not usable in production. | The substance-mapping feature had full lifecycle governance (review/approve/reject/audit) but no creation entry point had been built. | Added `POST /api/regx/v1/fda-data/mappings/substances/proposals/` (`SubstanceMappingProposalView` in `backend/fda_data/views.py`, `SubstanceMappingProposalSerializer` in `backend/fda_data/serializers.py`, gated by the new `CanProposeSubstanceMapping` permission — any user holding `fda_data.import` or `fda_data.review`). The endpoint accepts only proposal-shaped input (no `status` field is exposed; any `status` in the request body is ignored) and always creates the row as `PROPOSED`. Added the matching frontend "Propose substance mapping" action on `frontend/src/app/fda-data/mappings/page.tsx` (candidate fields, reason/evidence, confirmation dialog, success result explicitly stating no auto-approval) and `fdaData.mappings.proposeSubstance()` in `frontend/src/lib/api.ts`. Option A (manual proposal API) was chosen over Option B (import-generated candidates): it is sufficient for production operation because reviewers routinely encounter unmapped synonyms while working the mapping-review queue and need to originate a candidate without re-running an import, and it has materially lower blast radius than modifying the working, already-tested IID import/candidate-generation pipeline. Import-generated candidate creation remains a natural follow-on, not a blocking gap, since the manual path already removes the shell/ORM dependency end-to-end. | `backend/fda_data/tests/test_substance_mapping_proposal.py` — authorized reviewer/doer create `PROPOSED`; status cannot be supplied as `approved`; unauthorized user gets 403; invalid/superseded release rejected; cross-release/invalid canonical ingredient rejected (400); duplicate proposal handled deterministically; exact-UNII, exact-CAS, and manual reviewed-synonym proposal methods; ambiguous proposal remains `PROPOSED`; candidate-created audit event emitted with safe metadata; affected records reachable; proposal appears in the mapping-review list; proposal public ID is UUID-only; full `PROPOSED → UNDER_REVIEW → APPROVED` lifecycle via the shipped endpoints. Frontend: 2 new unit tests in `frontend/tests/unit/fda-iid.test.tsx` (propose dialog submits and shows a non-auto-approved result; API rejection surfaces in-dialog). 1 new Playwright E2E test in `frontend/e2e/fda-iid.spec.ts` covering propose → submit-review → approve end-to-end against mocked routes. | Backend CI, Frontend CI, Docker Integration CI on the final SHA. | Low-medium. Only one production creation path exists (manual proposal); an import-generated candidate path is not yet built. This is an accepted, explicitly-justified scope choice, not an unaddressed gap — the shell/ORM dependency this finding identified as blocking is fully removed. | **CLOSED** |
| HR-03 | Minor | `mapping.reviewer` was overwritten on every mapping action (submit-review, approve, reject, return), destroying the distinction between who reviewed a mapping and who later approved/rejected/returned it. | A single shared code path set `mapping.reviewer = request.user` unconditionally regardless of which action was being performed. | Added `rejected_by`/`rejected_at`/`returned_by`/`returned_at` fields to `SubstanceSynonymMapping` (migration `0003_substancesynonymmapping_rejected_by_and_more.py`). `_MappingActionViewBase` now branches by action: `reviewer`/`reviewed_at` are set only by submit-review and never touched again; `approved_by`/`approved_at` set only by approve; `rejected_by`/`rejected_at` set only by reject (falls back to `reviewer` only for the three legacy mapping types, which have no dedicated `rejected_by` field); `returned_by`/`returned_at` set only by return. `created_by`/`submitted_by`/`submitted_at` were already distinct fields and are unaffected. | `backend/fda_data/tests/test_mapping_lifecycle_transitions.py` and `test_mappings_api.py` assert `reviewer` is set only once (at submit-review) and is never overwritten by a subsequent approve/reject/return, and that `approved_by`/`rejected_by`/`returned_by` are recorded as the actual actor of each respective action. | Backend CI on the final SHA. | Low. Provenance fields are now single-write; any new mapping action must be added explicitly to the per-action branch in `_MappingActionViewBase` or it will silently fail to record an actor (fails closed on missing test coverage, not on silent overwrite). | **CLOSED** |
| HR-04 | Minor | Stale, non-approved mappings from superseded/rejected/unrelated releases could indefinitely block a legitimate fallback match against the currently active IID release. | `_unapproved_state_for()` in `backend/fda_data/substance_matching.py` collected mapping statuses across *all* matching mappings regardless of whether the mapping's own release was still usable (active/approved) for the current assessment. | `_unapproved_state_for()` now materializes candidate mappings with `.select_related("release")` and filters to `_release_usable(m)` before building the set of blocking statuses, so a non-approved mapping scoped to a superseded, rejected, or otherwise unusable release can no longer suppress a legitimate direct-`IIDIngredient` fallback match for the active release. Non-approved mappings scoped to the *current* usable release continue to fail closed (`REVIEW_REQUIRED`), as do conflicting approved mappings — this fix narrows scope, it does not weaken fail-closed behavior for in-scope conflicts. | `backend/fda_data/tests/test_substance_matching.py::TestStaleReleaseNeverBlocksFallback` — 4 named tests: stale `PROPOSED` mapping on a superseded release does not block fallback; a `PROPOSED` mapping on the *current* release still produces `REVIEW_REQUIRED`; a `REJECTED` mapping on the current release still fails closed; an `APPROVED` mapping scoped to a rejected/never-active release cannot leak into resolution for the active release (the direct-ingredient fallback applies instead). | Backend CI on the final SHA. | Low. Historical snapshots are unaffected — they resolve against the release they were taken against, not the currently-active one, so this change only affects new/live resolution. | **CLOSED** |

## Non-blocking findings referenced in the original review

Findings 3 (reviewer overwritten) and 4 (stale mapping may block fallback) are
tracked above as **HR-03** and **HR-04** respectively, and are both closed by
this remediation.

## Summary

All four findings (1 Critical, 1 Major, 2 Minor) from the original PR #5
human-review gate are closed as of this remediation. No new Critical or
Major finding was introduced by the remediation itself (see the second
focused review recorded separately). This document does not authorize
merging PR #5, ingesting real FDA data, using client formulation data, or
beginning Milestone 4D — those remain separately gated.
