# Milestone 4D Design-Review Remediation

This document records the remediation of the findings from the first
focused design-review gate performed against PR #7
(`regx/design/milestone-4d-discovery` → `regx-main`), which returned an
overall result of **FAIL** — material, correctable design gaps, not a
rejection of the underlying architecture. It supplements, and does not
remove or rewrite, the original review record. It follows the same
traceability-table convention already established for
[HUMAN_REVIEW_PR5_REMEDIATION.md](HUMAN_REVIEW_PR5_REMEDIATION.md).

Original review result: **FAIL** — 4 blocking design gaps, several
non-blocking corrections, all five original open questions analyzed and
four resolved (one explicitly deferred as a regulatory-content decision).

This is a **documentation-only** remediation. No code, migrations, CI, or
Docker configuration exists for Milestone 4D at any point in this
process — every correction below is a revision to
[MILESTONE_4D_DISCOVERY.md](MILESTONE_4D_DISCOVERY.md) itself.

## Traceability table

| ID | Severity | Original gap | Root cause | Correction made | Closure status |
|---|---|---|---|---|---|
| DR-01 | Blocking | The question data-source classification was a four-way split (`FDA_DERIVED_DEFAULT`/`USER_REQUIRED`/`SYSTEM_CALCULATED`/`REVIEWER_CONFIRMED`) with no way to represent a value whose authority comes from an attached evidence document rather than a bare user assertion. | The original design conflated "user-supplied" with "user-supplied and independently verifiable via an attachment" — these have different trust/audit requirements but were given the same classification. | Added a fifth `data_source_type` value, `EVIDENCE_DERIVED` (§3), requiring an attached evidence document before the answer counts as complete. Also added `ChecklistQuestion.prefill_source` (§3a) as a metadata sub-attribute — not a sixth top-level category — so a tenant-master-derived convenience prefill (e.g. from `FormulationComponent`) is never confused with FDA-derived data, without fragmenting the core classification. | **CLOSED** |
| DR-02 | Blocking | `ChecklistDefinition.status` named six lifecycle values (`draft`/`under_review`/`approved`/`active`/`superseded`/`retired`) but the document never specified the transition table governing them — the same category of omission HR-01 (Milestone 4A–4C's Critical finding) taught this codebase to treat as unacceptable. Separately, `AssessmentSnapshot`'s existing `clean()` immutability guard was found, on direct inspection, to be dead code — never invoked via `full_clean()` anywhere in the request path, so its immutability today is incidental (no update endpoint exists), not enforced. | The definition model was specified by field list only; the lifecycle table pattern proven for `fda_data`/`ChecklistExecution` was not applied symmetrically to `ChecklistDefinition`. The `AssessmentSnapshot` finding was a pre-existing defect elsewhere in the codebase that this design would have silently repeated if not caught. | Added §1a: a full `ChecklistDefinition` transition table (`submit_review`/`approve`/`reject`/`activate`/`supersede`/`retire`), mirroring `FDADataSourceRelease` release governance exactly, including a DB-level "one active definition per code" constraint. Added an explicit mutation-boundary immutability requirement to `ChecklistResponse` (§7) and a corrected description of `AssessmentSnapshot`'s actual (unenforced) behavior (§18), with a required implementation-phase acceptance criterion that `full_clean()` must actually be invoked at every save attempt once an execution is `approved` — not left as an unreachable model-level comment. | **CLOSED** |
| DR-03 | Blocking | `ChecklistQuestion.applicability_rule` was named as a field but its evaluation mechanism was never designed — a genuine gap, since the wrong answer (a free-text expression interpreted dynamically) would reopen the "arbitrary executable content in governed data" risk this codebase has consistently closed elsewhere (no eval, no stored executable expressions, allow-listed calculation bindings only). | The field was sketched at the model level without a corresponding design pass for how it would actually be evaluated safely. | Added §9a: a structured JSON condition-tree format with a fixed, small operator vocabulary (`eq`/`in`/`exists`/`not_exists`, composed via `all`/`any`), evaluated by a small pure-Python dispatch table — no `eval`/`exec`, no arbitrary attribute access, fields drawn only from a fixed allow-listed set. Also corrected an internal inconsistency this closure introduced and then caught: the worked example's MDE-unavailable case (§19 Q7) is a *blocked calculation* (`FDA_VALUE_UNAVAILABLE`), not a `NOT_APPLICABLE` result — `NOT_APPLICABLE` is reserved for when no IID precedent match exists at all (§3a/§9a), a distinction now stated explicitly to prevent the two states being confused during implementation. | **CLOSED** |
| DR-04 | Non-blocking (correction required) | This document understated the actual `CalculationStatus` enumeration by one value (`REGULATORY_REVIEW_REQUIRED` was omitted) and misquoted the six calculation function names (dropped the `calculate_` prefix). It also under-credited `CalculationResult`, which already carries `formula_identifier`/`formula_version`/`rounding_rule`/`reason_code`/`input_provenance` — more than `CalculationOutcome`'s original field list reflected. | The original document was written from a paraphrased understanding of `iid_assessment/calculations.py` rather than a direct line-by-line read. | Corrected the full nine-value `CalculationStatus` set and exact function names in §6 and §9. Expanded `CalculationOutcome` (§9) to mirror `CalculationResult`'s actual fields near-verbatim (`formula_version`, `rounding_rule`, `reason_code`, `input_provenance`) rather than re-deriving a thinner subset. Documented that formula versioning today is one global string shared by all six functions, not independently versioned per formula — a pre-existing property of `iid_assessment`, not something Milestone 4D changes, with the new field shape already having room to carry per-formula versioning if `iid_assessment` adopts it later. | **CLOSED** |
| DR-05 | Blocking | The `answer_type` enum (`boolean`/`decimal`/`text`/`choice`/`attachment_reference`) was too coarse to represent the question shapes IIG checklists actually need, and the `ChecklistExecution` state machine was missing two states (`cancelled`, `superseded`) that are genuinely distinct governance-relevant transitions, not merely readiness flags. | The original sketch prioritized illustrating the core classification/lifecycle mechanics over a complete type/state inventory. | Expanded `answer_type` to eleven values (§6a): `integer`, `decimal`, `text`, `long_narrative`, `date`, `yes_no_na` (a deliberate three-state type, distinct from plain `boolean`, so "not applicable" is never conflated with "no"), `single_select`, `multi_select`, `fda_record_reference`, `formulation_component_reference`, `attachment_reference`. Added `cancelled` (abandoned before review, distinct from a reviewer's `rejected`) and `superseded` (an approved execution whose FDA-release/formulation basis has since changed — never automatic, always a deliberate human action) to the `ChecklistExecution` transition table (§8a). Explicitly recommended *against* adopting the richer `DATA_ENTRY_COMPLETE`/`CALCULATED`/`REVIEW_COMPLETE` states the review's own checklist suggested, on the grounds that they describe readiness, not governance-relevant transitions, and would add complexity without a corresponding benefit — this is a considered rejection, not an oversight. | **CLOSED** |
| DR-06 | Non-blocking (decisions to finalize) | Three of the five open design questions (new app vs. extending `iid_assessment`; evidence-attachment lifecycle; CSV-safety helper promotion) had clear recommendations already, but were left in an "OPEN QUESTION" state rather than formally decided, and the review found no explicit statement resolving them into the design. | The original document correctly identified these as decisions needing to be made, but the revision pass requested by this remediation had not yet occurred to formally close them. | All three, plus the "one execution per formulation-version" question (the most structurally load-bearing of the five, since a wrong choice would force a breaking migration once execution-model implementation began), are now marked **DECIDED** in place (§1, §8, §15, §17), each retaining its original reasoning rather than silently dropping it. The fifth (exact checklist-template content to ship) is explicitly marked **DEFERRED**, not decided — this is stated as a regulatory-content decision that should not be resolved unilaterally by engineering judgment, consistent with the review's own recommendation, and is confirmed non-blocking for schema/execution/calculation-binding work (4D-1 through 4D-3). | **CLOSED** (4 of 5 resolved; 1 of 5 explicitly and correctly deferred, not left ambiguous) |
| DR-07 | Non-blocking (mandatory disclosure) | The design claimed the `documents` app's storage/malware-scan pipeline was reusable for evidence attachments without disclosing that the scan pipeline itself (`StubScanner`) is the production default in every configuration in this repository, and that `ClamAVScanner` — while functionally complete — is wired to a live clamd service nowhere in this repo. | The reuse claim conflated "the storage/tenant-isolation plumbing is reusable" (true) with "the scan pipeline is production-ready" (not true), without distinguishing the two. | §15 now explicitly discloses the stub-only status by name, states plainly that Milestone 4D inherits this gap unchanged and does not resolve it, and adds a corresponding bullet to §20 ("what this milestone explicitly does not do") so the limitation is stated in two places a reader is likely to look, not buried in one paragraph. | **CLOSED** |
| DR-08 | Non-blocking | Recalculation semantics (what happens when a draft input answer changes before submission) and the override-approval routing (does every override need its own approval, or does one execution-level approval cover all of them) were never specified, leaving both ambiguous for implementation. Export design also lacked a checksum field and an explicit PDF/Word scope decision. | These were implementation-relevant behaviors implied by the surrounding design but never stated outright. | Added §8b: while `draft`, editing an input re-triggers in-place recomputation of dependent `SYSTEM_CALCULATED` answers; once `submitted_for_review`, all responses lock until an explicit `return`. Added to §12: overriding requires at minimum `iig_checklist.review` (excluding Doer-equivalent actors), and exactly one execution-level `approve` action is the sole approval point covering every override an execution contains — no granular per-override routing. Added to §17: a SHA-256 checksum over the canonical export payload, audit-logged at generation time; JSON/CSV explicitly in scope for 4D, PDF/Word explicitly deferred with reasoning (no generated-document pipeline exists anywhere in this repo today). | **CLOSED** |

## Summary

All four blocking design gaps (DR-01, DR-02, DR-03, DR-05) and all
non-blocking corrections (DR-04, DR-06, DR-07, DR-08) identified by the
first design-review pass are addressed in the revised
[MILESTONE_4D_DISCOVERY.md](MILESTONE_4D_DISCOVERY.md). This remediation
does not authorize implementation of Milestone 4D, does not modify any
backend or frontend code, creates no migrations, and does not change CI
or Docker configuration. PR #7 remains in **draft** pending a second
focused design-review pass confirming these corrections are sufficient.
